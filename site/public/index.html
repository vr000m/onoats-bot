Record both sides. Keep the files.

onoats records your microphone and your computer's audio on separate streams, transcribes each one, and writes JSONL and Markdown you can read, search and move. No database. No account.

Two sources, never mixed

Each source has its own socket, its own speech-to-text session and its own tag. Nothing sends one source to both. Who spoke is a fact of how the audio was captured, not a guess from the sound.

On macOS 14.4 or later, system audio comes from a native Core Audio tap, so you don't need a virtual loopback driver. On other platforms the CLI uses PortAudio, and system audio needs a loopback device.

What you get

A menu-bar app
Start, Stop and Flush from the menu bar, with live levels for both channels and the state of speech-to-text.
Your choice of speech-to-text
Local Whisper-MLX on Apple Silicon, or a WebSocket server such as pipecat-local-stt-server.
Split remote speakers
Opt in to the Nemotron diarizer on Apple Silicon and the them channel gets S1, S2 and so on, live. If labelling fails, transcripts keep flowing without labels.
Failures you can see
Capture, speech-to-text and storage errors exit non-zero and say why. A partial session still lands in the queue.
Files in your own folders
Config, queue and transcripts live in directories you choose. Environment variables override the config file.
A CLI everywhere
Linux, Windows and Intel Macs run the CLI with PortAudio. The menu-bar app and native capture need Apple Silicon and macOS 14.4+.

The queue is a folder

The recorder moves each finished session into sessions/pending/ with an atomic rename, so a consumer never sees half a file. Run onoats convert, or point your own tool at the folder.

sessions/
  pending/   the recorder publishes here
  claimed/   a consumer moves a file here
  done/
  failed/

The menu-bar app and the CLI read the same config.toml. A running session keeps the settings it started with.

After the call

onoats convert renders each session to transcripts/<category>/<date>/<session_id>.md. From there the files are yours. Here is a workflow that builds on them, with the prompts I use for each step.

  1. Pull out action points

    Every line is tagged me or them, and S1, S2 when speakers are labelled. A model can read who said what and assign each commitment to the person who made it.

  2. Split long calls by topic

    Run a model such as Gemini, Claude Haiku or ChatGPT's Luna over a long transcript to cut it where the topic changes, and to find action points within each topic.

  3. Consolidate into living documents

    Group transcripts into topic folders, or into one document per topic that grows as related calls arrive.

  4. Build the digests

    An agent such as Hermes or pi.dev can build weekly, monthly or per-topic summaries from those folders.

onoats stops at the files. These steps run in your own tools, on the queue and the Markdown it writes.

Install

Apple Silicon with macOS 14.4 or later gets the menu-bar app and native system-audio capture. The first run asks for microphone and system-audio permission.

macOS app and native capture

git clone https://github.com/vr000m/onoats-bot.git
cd onoats-bot
make -C native setup

Needs the Xcode Command Line Tools and uv.

Any platform, CLI only

uv tool install onoats
onoats init
onoats bot

See the installation guide for loopback setup and extras.
